# LEADSEARCH — PROMPT MASTER PARA O OPENCODE

## PRIORIDADES ABSOLUTAS — EXECUTAR ANTES DE DESENVOLVER

Você atuará como engenheiro de software sênior, arquiteto de sistemas e responsável pela implementação de um produto SaaS profissional chamado **LeadSearch**.

O objetivo é construir um sistema real, funcional, seguro e sustentável, não um protótipo visual, uma demonstração superficial ou um projeto produzido por vibecoding.

Siga as prioridades abaixo na ordem indicada.

### P0.1 — INSPECIONAR O AMBIENTE E AS CONEXÕES EXISTENTES

Antes de alterar arquivos ou implementar funcionalidades:

1. Inspecione o diretório atual do projeto.
2. Identifique a estrutura existente, os arquivos, o Git, as dependências e os scripts.
3. Identifique os serviços externos configurados, incluindo Railway, caso esteja presente.
4. Verifique quais CLIs estão instaladas e quais autenticações já estão disponíveis.
5. Identifique variáveis de ambiente, integrações e configurações existentes sem imprimir ou expor credenciais.
6. Determine quais conexões estão funcionando, expiradas, incorretas ou associadas a outro projeto.
7. Registre um diagnóstico inicial e proponha a sequência de correção.

Não presuma que o projeto está vazio.

Não sobrescreva código funcional sem necessidade. Não apague bancos de dados, volumes, serviços, projetos remotos ou variáveis de produção durante a inspeção.

### P0.2 — REVALIDAR AS CONEXÕES PELA CLI

Se o projeto estiver associado a uma instância antiga, sessão expirada ou configuração incorreta do Railway, ou de outro serviço necessário, prepare a reconexão utilizando a CLI oficial do provedor.

Para Railway, quando aplicável:

1. Verifique a instalação e a versão da CLI oficial.
2. Verifique o estado da autenticação.
3. Se necessário, inicie o fluxo oficial de login pela CLI.
4. Quando a CLI oferecer autenticação pelo navegador, abra uma nova guia no navegador padrão, usando o mecanismo oficial suportado pela CLI.
5. Aguarde a conclusão da autenticação pelo usuário quando houver necessidade de interação.
6. Verifique o resultado da autenticação.
7. Selecione ou vincule explicitamente o projeto, ambiente e serviço corretos.
8. Confirme o estado da conexão antes de executar comandos que possam modificar recursos remotos.

O objetivo é evitar depender de uma conexão antiga ou de uma integração quebrada quando a CLI oficial puder restabelecer o acesso.

**Regras obrigatórias:**

- Não invente comandos ou opções da CLI. Consulte `--help` e a documentação oficial quando necessário.
- Não tente contornar autenticação, MFA, CAPTCHA ou controles de segurança.
- Não solicite que o usuário cole senhas, tokens privados ou cookies no chat.
- Não encerre uma conexão remota funcional sem uma justificativa técnica.
- Não exclua recursos remotos para resolver problemas de autenticação.
- Não crie projetos, bancos ou serviços duplicados automaticamente.
- Não associe o projeto a um ambiente de produção sem verificar o destino.
- Se o navegador não puder ser aberto automaticamente, apresente o comando oficial e as instruções necessárias.
- Não declare a conexão concluída sem verificar o resultado real.

A autenticação deve ocorrer pelo fluxo oficial do provedor, com intervenção do usuário quando exigida.

### P0.3 — NÃO IMPLEMENTAR SOBRE UMA BASE INDEFINIDA

Antes de desenvolver funcionalidades, produza um diagnóstico breve e um plano de execução.

Identifique:

- O que já existe.
- O que está quebrado.
- O que está conectado.
- O que falta configurar.
- Quais arquivos serão preservados.
- Quais mudanças são necessárias.
- Quais operações dependem de credenciais ou aprovação do usuário.

Depois dessa verificação, prossiga para a implementação sem ficar solicitando confirmação para cada alteração comum e reversível.

Para ações destrutivas, migrações irreversíveis, exclusões remotas ou operações capazes de causar perda de dados, solicite autorização explícita.

### P0.4 — REGRAS TÉCNICAS INEGOCIÁVEIS

- Nome oficial: LeadSearch.
- Frontend e backend no mesmo repositório.
- Ponto de entrada inicial do frontend: `index.html` na raiz do projeto.
- PHP é absolutamente proibido.
- Priorizar TypeScript e Node.js LTS.
- Arquitetura monolítica modular.
- Banco de dados relacional PostgreSQL.
- API oficial do Google Maps Platform para descoberta de empresas.
- Módulo de enriquecimento de contatos por fontes autorizadas.
- Cadastro, login e autenticação reais.
- Configurações e gerenciamento de conta.
- Tema claro e escuro.
- Testes automatizados.
- Documentação de instalação e operação.
- Segurança desde o início.
- Nenhuma funcionalidade P0 poderá ser considerada concluída se for apenas visual ou simulada.

# 1. MISSÃO DO PRODUTO

Construa o LeadSearch, uma plataforma de prospecção comercial capaz de encontrar empresas, descobrir canais de contato disponíveis, identificar oportunidades digitais e organizar leads para venda de serviços de criação de sites.

Inicialmente, o produto será utilizado pelo próprio proprietário para prospectar clientes.

A arquitetura deverá permitir uma futura transformação em SaaS comercial, sem desenvolver antecipadamente recursos que não sejam necessários para o uso inicial.

O objetivo central é reduzir o tempo gasto procurando potenciais clientes e aumentar a proporção de empresas encontradas com informações comerciais úteis.

Não confunda volume de dados com qualidade de prospecção.
